## KH-001：Mock 與真實測試，各自能證明什麼？

**問題來源**：2026-09-25，Andrew 提到 mock 無法涵蓋隨機錯誤與資料，要求改用真實資料測試。[原問答任務](codex://threads/01a0ce13-0aba-7183-a973-454d8af288fb)，使用者訊息 `01a0d771-bdf1-7302-a193-d1ea4280c7e9`。已實際讀取該問題及緊接的回答。

相關追問（間接來源：question_memory 摘要，不是原文）：2026-09-25 問刻意設成唯讀的 raw 寫入失敗測試，是否該換成實務上更常見的錯誤（[Q-20260925-youbike-failure-test-realism-v2-count-retired](../../question_memory/entries/Q-20260925-youbike-failure-test-realism-v2-count-retired.md)）；2026-09-26 問首次 DB 連線就失敗時，前後列數檢查是否還必要（[Q-20260926-youbike-connect-count-necessity-count-retired](../../question_memory/entries/Q-20260926-youbike-connect-count-necessity-count-retired.md)），以及是否要窮舉每種分支、測試做到多少才算夠（[Q-20260926-youbike-test-scope](../../question_memory/entries/Q-20260926-youbike-test-scope.md)，早於 D1 固定六案例的定案）；同日 T5／T6 改為邏輯測試（[Q-20260926-youbike-test-scope-v5](../../question_memory/entries/Q-20260926-youbike-test-scope-v5.md)）。

**為何收錄**：這裡有兩件容易混在一起的事：「自己準備不同情況」與「接觸真實服務」。值得釐清這個差別，但不能把選擇真實測試當成不懂測試。

**白話重點**：Mock 像練習時的代班演員，你可以安排它這次成功、下次報錯，甚至用資料產生器提供很多不同輸入；但演員演得再像，也不能證明真正的 API、網路和資料庫此刻能一起工作。真實整合測試則真的走過這些環節，能發現假設與現實不同的地方；不過今天服務正常，不代表逾時或斷線時也會正確處理。

**小例子**：

- 安排「回應為空」：可重複檢查程式怎麼面對空資料；這是受控情境。
- 真的抓 YouBike，保存後從 DB 查回：能檢查這一次資料有沒有走完整條路。
- 連續成功十次：只增加正常情況的觀察，不能當成已測過十種故障。

隨機產生資料是另一個維度：假資料或真實來源都可能變動。隨機也不保證覆蓋重要邊界，出了錯還需要保留能重現的輸入。

**測試做到多少才夠（9/26 追問）**：不用窮舉每種輸入與分支組合。依已確認的驗收，挑正常路徑、重要的失敗行為與邊界；走同一條處理路徑的用一個代表案例，會造成不同資料後果的才分開驗。分支覆蓋率高，不等於驗收完整。每個階段先列固定案例與停止條件，D1 最後固定為六個案例。

**在專案哪裡用**：D1 六個案例各用最能證明該行為的方式：T1 用官方真實 API＋隔離測試 DB（`youbike_test`）；T2 用官方網域上不存在的路徑，取得真實 404；T3 讓產品連到本機已關閉的 port，得到真實的連線拒絕；T4 用本機 listener 做出真實的讀取逾時；T5／T6 只驗產品自己的容量與時間判斷，改用模擬回應直接提供 bytes 與碼錶讀值（9/26 依 Andrew 要求簡化）。若要比對站點資料，使用同一次抓取並保存的 raw；不要再抓第二次即時 API 當答案，因為兩次之間來源可能已更新（起始測試的站點對帳已於 9/25 取消，這裡只說原則）。

**後續應用證據（2026-09-25～26）**：

- Andrew 質疑刻意設唯讀的寫入失敗是否貼近實務；C 案例後來改成 DB 連線失敗（DB 未啟動／port 錯誤）。
- 首次連線就失敗、還沒有任何寫入時，前後列數證明不了新的事；該案例移除列數檢查，只驗錯誤類型與訊息。
- Andrew 同意「只驗容量／時間判斷時，可以直接提供 bytes 與時間值」，T5／T6 改成邏輯測試，T4 保留真實 TCP 等待。

這些顯示已能依「這個測試要證明什麼」選擇真實或受控方式；仍持續觀察，不視為已掌握。

**容易搞混**：「這次成功」不等於「所有情況都可靠」；「mock 可以安排多種資料」也不等於「mock 能證明真實服務正常」。T5／T6 的模擬回應只提供輸入，錯誤仍由產品自己的判斷拋出，所以驗的是產品邏輯，不是 HTTP 傳輸；替身寫法（`lambda *args, **kwargs: response`、`__enter__`）見 [engineering_challenges_log.md](engineering_challenges_log.md)「`*args`、`**kwargs`」與「模擬 HTTP 回應、容量與時間測試」兩節。這份筆記只解釋差別，不新增 mock 作業。

**一句話記法**：受控測試檢查「指定情況下會怎樣」；真實測試檢查「這次真實連起來會怎樣」。

## KH-002：外鍵與父子表共用 batch_id：FK 只查不填

**問題來源**（間接來源：question_memory 摘要，不是原文）：2026-09-23～24 連續五次相關提問：外鍵要不要明寫、欄位同名會不會自動對上（[Q-20260923-postgresql-fk-explicit-reference](../../question_memory/entries/Q-20260923-postgresql-fk-explicit-reference.md)）；同批 raw 與站點時間相同，為何時間 FK 仍要求唯一（[Q-20260923-youbike-shared-time-parent-fk](../../question_memory/entries/Q-20260923-youbike-shared-time-parent-fk.md)）；父表 ID 怎麼用 RETURNING／fetchone 取回給子表（[Q-20260924-insert-returning-fetchone-parent-child](../../question_memory/entries/Q-20260924-insert-returning-fetchone-parent-child.md)）；SQL 能否自己產生並讓子表共用（[Q-20260924-sql-generate-share-parent-child-id](../../question_memory/entries/Q-20260924-sql-generate-share-parent-child-id.md)）；batch_id 從產生到寫進兩張表的完整流向（[Q-20260924-batch-id-end-to-end-flow](../../question_memory/entries/Q-20260924-batch-id-end-to-end-flow.md)）。同期的存檔檢查見 [project_state.md](project_state.md) 9/23–9/24 歷史紀錄。

**為何收錄**：兩天內同一概念問了五次，同期存檔也反覆出現同類錯誤：被參照的父表欄位沒有唯一約束；把 UNIQUE 加到子表的 batch_id（會讓一批只能存一站）；子表欄位想用 `gen_random_uuid()` 再生一個值去對父表。之後已改對：Python 在請求前產生一次 `uuid4`，raw 與每筆站點 INSERT 都傳同一個值；父表 batch_id 與 fetched_start_at 加上 UNIQUE。9/25 依這份 SQL 建表，並真實寫入 1 筆 raw、1807 筆站點成功。

**白話重點**：外鍵（`REFERENCES`）像門口查名單：子表寫進來的值，必須在父表那一欄找得到。它只負責「查」，不負責「填」。

- 欄位同名不會自動連起來，要明寫 `REFERENCES 父表 (欄位)`；名字不同也可以參照。
- 值要由程式自己放進 INSERT，FK 不會從父表複製過來。
- 被查的父表欄位必須唯一（PRIMARY KEY 或 UNIQUE），否則資料庫不知道該對到哪一列，建表就會失敗。子表同一個值可以出現很多次（一批有很多站）。

**小例子**（訂單情境）：

```sql
CREATE TABLE orders (order_no TEXT PRIMARY KEY);
CREATE TABLE order_items (
    id SERIAL PRIMARY KEY,
    order_no TEXT NOT NULL REFERENCES orders (order_no)  -- 一張訂單可有多筆明細
);
-- orders 有 'A001' 時，兩筆明細都寫 'A001' 可以；寫 'Z999' 會被拒絕
```

如果 ID 由資料庫產生，可以用 `INSERT ... RETURNING order_no` 取回「這一次」產生的值，再傳給明細；`RETURNING` 是把剛寫入的值回傳，不是再生一個新值。

**在專案哪裡用**：[raw_response.sql](../sql/practice/raw_response.sql) 的 `raw_bytes`（父表，一次完整回應一列）與 `response`（子表，一站一次採樣一列）；[youbike.py](../src/extract/youbike.py) 第 25 行產生 `batch_id`，第 41 行的 raw INSERT 與第 77–86 行的站點 INSERT 都傳它。現行做法是 Python 產生；RETURNING 是 9/24 學過的另一種取法，沒有採用。

**容易搞混**：

- 父表有 PRIMARY KEY（`id`），不代表其他欄位也唯一；被參照的是哪一欄，就是那一欄要唯一。
- 現行兩條 FK（batch_id、fetched_start_at）各查各的，只保證兩個值各自存在，不保證來自同一列 raw；要綁在同一列需要複合關聯，屬 D3 schema 範圍，這裡不新增要求。
- FK 本身不禁止 NULL，必填要另加 NOT NULL；現行子表這兩欄都有 NOT NULL。

**一句話記法**：FK 只查不填；被查的父欄位要唯一，子表可以重複。

## KH-003：SQL 檔、資料表與 transaction 是三件事

**問題來源**（間接來源）：2026-09-23 同一天三問：raw body 與解析後的資料為何不放同一個 SQL 檔處理（[Q-20260923-youbike-sql-file-vs-transaction](../../question_memory/entries/Q-20260923-youbike-sql-file-vs-transaction.md)）；raw_response.sql 怎麼和資料庫串起來（[Q-20260923-youbike-sql-file-execution](../../question_memory/entries/Q-20260923-youbike-sql-file-execution.md)）；自己寫的 schema 怎麼變成指定 DB 裡的表（[Q-20260923-schema-definition-target-db](../../question_memory/entries/Q-20260923-schema-definition-target-db.md)）。

**為何收錄**：三題都在問「檔案裡的 SQL」和「資料庫裡實際發生的事」之間的關係，屬語法會寫、但用途和執行時機容易混在一起的類型。現行程式的交易切法（兩段連線、raw 先 commit）是正確的；建表依分工由 Codex 執行，這部分沒有新的應用紀錄可判斷，維持持續觀察。

**白話重點**：

- `.sql` 檔只是一張「指令清單」（文字檔），放著不會連到任何資料庫。
- 要有人拿連線去執行它：連線決定「在哪個 DB」，檔案內容決定「建什麼表」。執行並 commit 後，表才存在那個 DB；連測試庫執行，就只有測試庫有表。
- Python 寫入時只用表名和欄位名，不會回頭讀 `.sql` 檔；之後改檔案，也不會改到已建好的表，要另外執行 `ALTER TABLE` 之類的指令。
- transaction 是「執行時」的範圍：同一個 transaction 裡的寫入一起成功，或一起取消。它由連線與 commit 決定，和 SQL 寫在幾個檔案無關。

**小例子**（商店情境）：

```bash
psql -d shop_test -f schema.sql   # -d 選資料庫，-f 指定要執行的檔案
```

```python
with psycopg.connect(dsn) as conn:   # 區塊正常結束就 COMMIT；出錯就 ROLLBACK；最後關閉連線
    conn.execute("INSERT INTO orders (order_no) VALUES (%s)", ("A001",))
```

**在專案哪裡用**：[raw_response.sql](../sql/practice/raw_response.sql) 用一個檔案定義兩張表，這沒問題。[youbike.py](../src/extract/youbike.py) 用兩段獨立的 `with psycopg.connect(...)`：第一段（第 39–41 行）只寫 raw，離開區塊就 commit；第二段（第 43 行起）才解析並寫站點。所以站點驗證失敗時，第二段整批 rollback、不會留下部分站點，第一段已 commit 的 raw 仍在，日後可以重播。

**容易搞混**：

- 放在同一個檔案 ≠ 同一個 transaction；分成兩個檔案，也不會自動變成兩個 transaction。
- PostgreSQL 的「schema」還有另一個意思：表所在的命名空間（例如 `public`）。本題說的 schema，是 CREATE TABLE 裡的欄位、型別和約束。

**一句話記法**：檔案存指令，連線選資料庫，commit 才算數。

## KH-004：raw、JSON、bytes：同一份回應的不同說法

**問題來源**（間接來源）：2026-09-23 問 API 回應的每個欄位是否都要建 DB 欄位（[Q-20260923-youbike-raw-versus-parsed-columns-v2](../../question_memory/entries/Q-20260923-youbike-raw-versus-parsed-columns-v2.md)）、JSON 該拆成每站一列還是整包存 jsonb（[Q-20260923-youbike-jsonb-or-bytea-v2](../../question_memory/entries/Q-20260923-youbike-jsonb-or-bytea-v2.md)）、JSON 有哪些欄位要拆（[Q-20260923-youbike-json-column-mapping](../../question_memory/entries/Q-20260923-youbike-json-column-mapping.md)；其中 station_active 轉 boolean、raw_sha256 等內容已被後續決定取代，以現行 spec 與 SQL 為準）；2026-09-25 再問「body 能解析成 JSON，和 SQL 保存 raw 原始資料是否矛盾」（[Q-20260925-youbike-raw-json-bytes](../../question_memory/entries/Q-20260925-youbike-raw-json-bytes.md)）。

**為何收錄**：同一組觀念隔兩天又被問到，值得集中講清楚。另外，9/23 曾有「解析發生在 raw 保存之前」的說法讓人疑惑，那是助理用詞不清、已由 Andrew 指正（[Q-20260923-raw-memory-versus-db-persistence](../../question_memory/entries/Q-20260923-raw-memory-versus-db-persistence.md)），不算知識缺口；同日補正「引導沒先講資料表示」，同樣是引導問題。

**白話重點**：三個詞講的是不同面向，彼此不衝突：

- **raw**：來源回應「還沒加工」的狀態。
- **JSON**：這份內容的「格式」。
- **bytes／BYTEA**：Python 與 PostgreSQL 用來「裝」它的型別。

YouBike 回應本來就是「JSON 格式的一串 bytes」。raw 表整包存這串 bytes；解析（`loads`）是另外產生 Python 的 list／dict，原本的 bytes 不會被改掉。

**小例子**（感測器情境）：

```python
body = b'[{"id": "A01", "temp": 21.5}]'   # 收到的回應：bytes
records = json.loads(body)                 # 另外產生 list[dict]
type(body), type(records)                  # (bytes, list)；body 本身沒變
```

**在專案哪裡用**：

- `raw_bytes` 一列＝一次完整的 HTTP 回應（body 為 BYTEA，另有 batch_id 與採樣時間）。
- `response` 一列＝一站一次採樣，只拆 [platform_spec.md](platform_spec.md) §3.1 列出的來源欄位（sno、sna、sarea、latitude、longitude、Quantity、available_rent_bikes、available_return_bikes、act、srcUpdateTime）；其他來源欄位留在 raw，不必每個 JSON 欄位都建 DB 欄位。
- 順序：body 先在記憶體 → 寫進 raw 並 commit → 才解析、驗證、寫站點（見 KH-003）。
- 整包 jsonb 適合來源格式常變、或只做臨時查詢；本專案要按站、按時間統計，之後還要和天氣、行事曆 join，所以分析表採「一站一次採樣一列、欄位明確」。raw 已用 BYTEA 保存原樣，不必只因為來源是 JSON 就再多存一份 jsonb。

**容易搞混**：

- 「記憶體裡已經有 raw」和「raw 已 commit 進 DB」是兩件事；raw-first 指的是後者要發生在解析之前，不是說 JSON 比 raw 先出現。
- 「一站一列」不是「每個 JSON 欄位一列」。

**後續補充（2026-10-25，應用證據：本機 HTTP 假伺服器的回應也是 bytes）**：D11 的 HTTP fixture 自己準備一站資料時，走的是同一條路：Python 物件 → `json.dumps(...)`（`str`）→ `.encode("utf-8")`（`bytes`）。`wfile.write(...)` 只收 bytes；`Content-Length` 要填**位元組數**，不是字元數。例如 `[{"sna": "台北車站"}]` 在 `ensure_ascii=False` 時是 17 個字元、25 個位元組；預設的 `ensure_ascii=True` 把中文寫成 `\uXXXX`，兩者剛好相等（都是 37），所以預設情況不會出錯，改了參數才會露出差別（Python 3.9.6 實跑）。11/01 16:30 的存檔快照用 `len(body)`（`body` 是 bytes），與這個規則一致。

**一句話記法**：raw 是狀態、JSON 是格式、bytes 是型別；解析是另做一份，不改原件。

## KH-005：HTTP 串流與 with：內容只能讀一次，離開 with 就關閉

**問題來源**：2026-09-25 問分塊下載後如何接回保存與解析（間接來源 [Q-20260925-youbike-chunks-merge](../../question_memory/entries/Q-20260925-youbike-chunks-merge.md)）；同日兩次真實測試失敗（[Q-20260925-youbike-stream-consumed](../../question_memory/entries/Q-20260925-youbike-stream-consumed.md)、[Q-20260925-youbike-with-indent](../../question_memory/entries/Q-20260925-youbike-with-indent.md)，詳見 [project_state.md](project_state.md) 9/25 歷史紀錄）；2026-09-26 追問 contextmanager 的作用，以及它和 pytest fixture 的差別（[Q-20260926-youbike-contextmanager](../../question_memory/entries/Q-20260926-youbike-contextmanager.md)、[Q-20260926-youbike-fixture-contextmanager](../../question_memory/entries/Q-20260926-youbike-fixture-contextmanager.md)）。

**為何收錄**：同一天兩個可查證的實作錯誤，都和「資源的生命週期」有關：

1. 用 `iter_content()` 讀完後，又呼叫 `response.json()`，得到 `RuntimeError: The content for this response was already consumed`。
2. `with requests.get(...)` 裡只放了非 200 判斷，下載迴圈留在外面；回應先被關閉，body 變成空的，後面的 `loads(body)` 報 `JSONDecodeError`（那次已先 commit 了一筆 0 bytes 的 raw）。

兩者當天都已修正，真實測試通過；隔天又追問 context manager 的原理。

**白話重點**：

- `stream=True` 時，回應內容像水管裡的水：`iter_content()` 一段一段流出來，流完就沒了。要重複使用，就自己把流出來的 bytes 接住（`buffer`），之後都用接住的那份（`loads(body)`），不要再向 response 要一次。
- `with ... as response:` 區塊結束時會自動關閉回應。凡是要讀回應內容的程式，都要縮排在區塊裡；區塊外只能用已經存進變數的 bytes。
- chunk 只是同一份回應任意切下的一段 bytes，不是一站，也不是一份完整 JSON；所以大小檢查每段都做，解析要等全部收完。

**小例子**（檔案情境，道理相同）：

```python
with open("log.txt") as f:
    first = f.read()    # 讀到結尾
    again = f.read()    # 再讀只得到 ''，內容已經讀過了
print(first)            # 區塊外用變數；這裡再呼叫 f.read() 會出錯，因為檔案已關閉
```

**在專案哪裡用**：[youbike.py](../src/extract/youbike.py) 第 28–37 行：`with requests.get(url, stream=True, timeout=(5,10)) as response:` 裡面依序做非 200 判斷、逐塊累積（先檢查大小與時間再 `extend`）、`body = bytes(buffer)`；兩段 DB 區塊都在 with 外，只用 `body`。T5／T6 的測試替身設定 `response.__enter__.return_value = response`，就是讓產品的 `with ... as response` 拿到同一個替身（見 [engineering_challenges_log.md](engineering_challenges_log.md)「模擬 HTTP 回應、容量與時間測試」）。

**容易搞混**：

- 迴圈跑完 ≠ 回應已關閉：迴圈結束時回應還開著，直到離開 with。
- `@contextmanager` 和 `pytest.fixture` 都能「先準備、後收尾」：fixture 由 pytest 依測試的參數名自動提供，預設每個測試一份；contextmanager 由程式自己用 `with` 呼叫，區塊結束就收尾。收尾動作要自己寫（例如 `finally`），decorator 不會自動知道怎麼關資源。9/26 簡化測試後，用到 contextmanager 的 `local_body_server` 已移除，這段只保留原理。

**後續再現：DB 連線與 cursor 離開 with 也會關閉（2026-09-30～10-01，間接來源）**：同一個道理在資料庫上連續出現兩次可查證的錯誤，都已當場指出並修正（兩次的縮排都由助理依 9/26 小問題代修授權調整，不記成 Andrew 已獨立改對）。9/30 載入函式裡的 `for` 迴圈縮排在 `with psycopg.connect(...)` 區塊外面，執行時 `OperationalError: the connection is closed`（[Q-20260930-youbike-d4-a-third-draft](../../question_memory/entries/Q-20260930-youbike-d4-a-third-draft.md)）；10/01 查詢搬到迴圈前之後，又在已離開 `with conn.cursor() as cursor:` 的位置呼叫 `cursor.execute`，`InterfaceError: the cursor is closed`（[Q-20261001-youbike-d4-a-fetchall-shape](../../question_memory/entries/Q-20261001-youbike-d4-a-fetchall-shape.md)）。

- 連線的 `with`：正常離開時 commit（出錯則 rollback），**然後關閉連線**。cursor 的 `with`：離開就關閉 cursor，但不結束交易。[psycopg 3 的連線 with](https://www.psycopg.org/psycopg3/docs/basic/usage.html)、[cursor 的 with](https://www.psycopg.org/psycopg3/docs/api/cursors.html)
- 所以「縮排到哪裡」就是「資源能用到哪裡」：要執行 SQL 的那一行，得縮排在還開著的 `with` 裡；要在 cursor 區塊外再查，得另開一個 cursor，或用 `conn.execute`。
- 現行 `extract_youbike()`（10/14 存檔快照）可對照：`with psycopg.connect(...) as conn:` 包住整段流程，查鎖與查 raw 在第一個 `with conn.cursor() as cursor:` 內，下載完要寫入時另開第二個 cursor 區塊。

**一句話記法**：串流讀一次就要接住；讀 response 要在 with 裡，with 外只用接住的 body。

## KH-006：datetime：模組和類別同名；時區是標註還是換算

**問題來源**（間接來源：[project_state.md](project_state.md) 方向檢查紀錄）：2026-09-23 存檔的 `from datetime import DateTime` 造成 ImportError；2026-09-24 存檔的 `datetime.strptime(...)` 造成 `AttributeError: module 'datetime' has no attribute 'strptime'`；2026-09-25 修改時一度漏掉 `ZoneInfo` 的匯入（[Q-20260925-youbike-time-budget-check](../../question_memory/entries/Q-20260925-youbike-time-budget-check.md)；該條其餘的時間檢查點派作已於 9/25 取消）。

**為何收錄**：連續兩天的錯誤都出在「datetime 模組」和「datetime 類別」同名，屬語法／工具類。現行程式已改成 `from datetime import datetime as DateTime, timezone`；9/24 改正後，9/25 起真實擷取與寫入站點都正常。

**白話重點**：`datetime` 是一個模組（一個 .py 檔），裡面有一個同名的類別也叫 `datetime`。

- `import datetime`：拿到的是「模組」；`strptime`、`now` 屬於類別，要寫 `datetime.datetime.strptime(...)`。
- `from datetime import datetime`：直接拿到「類別」。
- `as` 只是幫匯入的東西取別名。模組裡本來沒有叫 `DateTime` 的東西，所以 `from datetime import DateTime` 會失敗，要寫 `from datetime import datetime as DateTime`。名稱有分大小寫。

**小例子**：

```python
import datetime
datetime.datetime.strptime("2026-01-05 09:30:00", "%Y-%m-%d %H:%M:%S")  # 可以

from datetime import datetime as DT
DT.strptime("2026-01-05 09:30:00", "%Y-%m-%d %H:%M:%S")                 # 也可以
```

**在專案哪裡用**：[youbike.py](../src/extract/youbike.py) 第 6 行匯入別名 `DateTime`；第 22 行 `DateTime.now(timezone.utc)` 取得帶時區的 UTC 採樣時間；第 72–74 行先把來源時間字串 `strptime` 成沒有時區的時間，再 `.replace(tzinfo=ZoneInfo("Asia/Taipei"))` 標上台北時區，最後 `.astimezone(timezone.utc)` 換算成 UTC（spec §3.1：來源沒有 offset 時按 Asia/Taipei 解讀）。

**容易搞混**：

- `strptime` 產生的是沒有時區（naive）的時間。`replace(tzinfo=...)` 是「標註它本來是哪個時區」，時鐘數字不變；`astimezone(...)` 才是「換算成另一個時區」，數字會變。兩者不能互換。例：台北 08:00 標註後換算，得到 UTC 00:00。
- 函式裡用到、卻沒匯入的名稱（例如那次漏掉的 `ZoneInfo`），只 import 模組時不會報錯，要等執行到那一行才出 `NameError`；所以「import 成功」不代表函式裡每個名稱都沒問題。
- `from time import monotonic` 同樣是把名稱放進本模組，所以 T6 要替換 `src.extract.youbike.monotonic`（見 KH-009）。

**一句話記法**：`import datetime` 拿到整個盒子，`from datetime import datetime` 才拿到盒子裡的工具；replace 是貼標籤，astimezone 才是換算。

## KH-007：欄位型別驗證：檢查的是值，bool 也算 int

**問題來源**（間接來源：[project_state.md](project_state.md) 9/24 方向檢查、[Q-20260927-youbike-d2-integer-guidance](../../question_memory/entries/Q-20260927-youbike-d2-integer-guidance.md)）：2026-09-24 的 check_json 有幾個問題：`isinstance(row, type)` 檢查了整個 dict 而不是欄位值（合法站名也被拒）；來源型別設錯（sno 設成 int、act 設成 bool、srcUpdateTime 設成 datetime，但來源其實都是字串）；非字串欄位不能 `strip()`。2026-09-27 一次性呼叫確認：現行 check_json 會接受 `-1` 和 `True`。

**為何收錄**：同一個函式連續出現可查證的型別判斷錯誤。9/24 的問題已修正：改成檢查 `row[col]`、act 改 str、只對文字做 `strip()` 由 Andrew 修改；sno、srcUpdateTime 改 str 是 Andrew 指定由 Codex 代改。bool 與負數正是 D2.A 目前要做的部分；這裡只補觀念，不寫 D2 的答案。

**白話重點**：

- `isinstance(值, 型別)` 要放「欄位的值」，也就是 `row[col]`，不是整個 `row`（整個 row 永遠是 dict）。
- 預期型別要照「來源實際的樣子」，不是照「最後想存成什麼」：YouBike 的 sno 是保留前導零的文字、act 是文字 `"0"`／`"1"`、時間是待解析的文字；車數是 JSON 數字。
- 在 Python 裡，`bool` 是 `int` 的子類別，所以 `isinstance(True, int)` 是 `True`。只靠 `isinstance(x, int)` 擋不住布林值；「不能是負數」則是型別以外的另一個條件。

**小例子**（問卷年齡欄位情境，非專案程式）：

```python
isinstance(True, int)   # True：bool 是 int 的子類
isinstance(1.5, int)    # False
isinstance(-3, int)     # True：型別對了，不代表數值合理
```

**在專案哪裡用**：[youbike.py](../src/extract/youbike.py) 第 12–19 行的 `check_json`，以及第 50–59 行十個欄位的呼叫。依據是 [platform_spec.md](platform_spec.md) §3.1（例如 Quantity 為非負整數，拒絕 bool 與小數；sno 保留前導零、不轉整數）；D2.A 的精確案例見 [de_transition_plan.md](de_transition_plan.md)「2026-09-27 D2接續」。

**容易搞混**：型別檢查和數值範圍檢查是兩層：`-3` 的型別是 int，仍可能不合法；`True` 在數值上等於 1，型別上卻是布林值。

**一句話記法**：驗值不驗整列、照來源型別驗；True 也是 int，型別對了還要看範圍。

## KH-008：pytest.raises：拋錯後的程式不會執行；match 是搜尋

**問題來源**（間接來源）：2026-09-26 問「pytest.raises 區塊內，呼叫之後的 assert 為何要移到區塊外」（[Q-20260926-youbike-db-check-raises-scope-count-retired](../../question_memory/entries/Q-20260926-youbike-db-check-raises-scope-count-retired.md)）；同日 404 測試失敗，原因是 match 字串少一個冒號（[Q-20260926-youbike-http404-match](../../question_memory/entries/Q-20260926-youbike-http404-match.md)）；T5 說明也提到 match 的 `^`、`$`（[Q-20260926-youbike-size-test](../../question_memory/entries/Q-20260926-youbike-size-test.md)）。

**為何收錄**：這是原理追問，同一天又有一次「測試期待的字串不符」的真實失敗；會用 pytest.raises，但區塊範圍和 match 的比對方式容易誤會。相關測試修正後都已通過。

**白話重點**：

- `with pytest.raises(X):` 的意思是「這個區塊裡應該拋出 X」。一旦拋出，區塊裡剩下的程式都會被跳過。所以檢查錯誤內容的 assert 要放在 with 外面（用 `as errinfo` 接住），區塊裡最好只放預期會拋錯的那一行。
- `match` 不是「完全相等」，而是用正規表示式在錯誤訊息裡「搜尋」（`re.search`）：只寫一段也能配對；要求整句一模一樣，就加 `^` 和 `$`。訊息裡若有 `.`、`(`、`?` 這類在正規表示式有特殊意義的字元，要跳脫（例如 `re.escape()`）。
- 測試失敗時先分清楚：是產品行為錯，還是測試的期待寫錯？9/26 那次產品訊息正確，是 match 少了冒號。

**小例子**（問卷情境，`check_age` 為虛構函式）：

```python
with pytest.raises(ValueError) as errinfo:
    int("abc")
    print("不會執行")                  # 上一行已拋錯，這行被跳過
assert "invalid literal" in str(errinfo.value)   # 放在區塊外才會執行

with pytest.raises(ValueError, match=r"^age must be >= 0$"):   # 整句必須相同
    check_age(-1)
with pytest.raises(ValueError, match="must be"):               # 訊息含這段就算
    check_age(-1)
```

**在專案哪裡用**：[test_youbike_extract.py](../tests/unit/test_youbike_extract.py) 的 `test_db_failure`（區塊內只呼叫一次 `extract_youbike()`，區塊外檢查訊息含 `Connection refused` 與 port）、`test_http_404`、T5、T6（`match=r"^...$"` 整句比對）。

**容易搞混**：

- `match` 比對的是 `str(例外)`，不是例外類別的名稱；類別由第一個參數檢查。
- 第一個參數也接受子類別：寫 `Exception` 幾乎什麼錯誤都接得住，所以 404 測試同時用 match 鎖住訊息，別的錯誤才不會被當成 PASS。

**後續再現（2026-09-30 D3.D 第四版，間接來源 [Q-20260930-youbike-d3-d-fourth-draft](../../question_memory/entries/Q-20260930-youbike-d3-d-fourth-draft.md)）**：測試把「準備 raw A／B」放進 `with pytest.raises(ForeignKeyViolation):` 區塊裡。準備動作自己先拋出同型的錯誤，pytest 接住後離開整個區塊，後面真正要驗的「混搭 INSERT」根本沒執行，但測試仍顯示 `1 passed`；當時用行號追蹤才確認第五例沒跑到，之後該情境已補齊，D3 完成。教訓和上面相同：`raises` 區塊只放預期會拋錯的那一行，準備資料放在區塊外；**綠燈不等於想驗的那一行真的執行了**。

**一句話記法**：拋錯之後的行不會跑；match 是搜尋，要整句就加 ^ 和 $。

## KH-010：fetchall → dictionary → tuple 比較：如何判斷同站重播

**問題來源**：2026-10-01 本次側對話可見原文。Andrew 依序追問 dictionary 的用途、fetchall 的回傳型別、其他欄位如何保存與取得、DB 與 body 的欄位順序，以及是否需要每欄各寫一個 if；最後明確要求 Codex 補寫比較區塊並收錄重點筆記。

**為何收錄**：把「多列資料」「單列 tuple」「用站點 ID 查整列的 dictionary」分開理解，才能看懂重播判斷。這次由 Codex 示範實作，不記成 Andrew 已能獨立完成。

**白話重點：每個變數裡放什麼？**

| 變數 | 來源／內容 | 用途 |
|---|---|---|
| `record` | 目前程式的 `fetchall()` 結果；psycopg 預設為 list 裡放 tuple | 保存查回的多列 DB 資料 |
| `existing` | `{r[1]: r for r in record}` | 用站點 ID 查到 DB 的整列資料 |
| `row` | `loads(body)` 後，迴圈正在處理的站點 dictionary | 用 `row["sno"]` 等欄位名稱取得來源值 |
| `parsed` | `parse_station(row)` 回傳的十欄 tuple | 本次來源資料，已驗證及轉型 |
| `db_row` | 從 `existing` 取出的該站完整 DB tuple | 第一項是 batch_id，其餘是十個來源欄位 |
| `db_values` | `db_row[1:]` | 去掉 batch_id，讓欄位順序對齊 `parsed` |

`fetchall()` 本身不會建立 dictionary。以下用三欄來源資料簡化示範，實際產品是十欄：

```python
record = [("batch-A", "S001", "台北車站", 10)]
existing = {r[1]: r for r in record}
# {"S001": ("batch-A", "S001", "台北車站", 10)}

db_row = existing["S001"]
# ("batch-A", "S001", "台北車站", 10)

db_values = db_row[1:]
# ("S001", "台北車站", 10)

parsed = ("S001", "台北車站", 10)
assert db_values == parsed
```

`{r[1]: r}` 的冒號左邊是 key，右邊是 value：**用站點 ID 查，查到完整一列**，不是只存站點 ID。索引 `[1]` 是第二欄，不是第一欄。建立 dictionary 不會改動 value 內 tuple 的順序，也不會再次查 SQL。

**欄位順序如何對齊？**

- DB tuple 的順序由 SQL `SELECT` 決定。目前是 `batch_id`，接著 `station_id, station_name, station_area, latitude, longitude, quantity, available_rent_bikes, available_return_bikes, station_active, source_update_time`。
- body 解析後的站點是 dictionary；`parse_station()` 用欄位名稱取值，因此 JSON 欄位原本的排列不重要。它的 `return` 才決定 `parsed` 的順序，恰好對應上面十個來源欄位。
- 所以 `db_row[1:]` 可以直接和 `parsed` 比較。Python 比較的是對應位置的值，不會自動依欄位名稱配對；修改 SELECT 或 return 的順序時，必須重新核對。

**在專案哪裡用**：[youbike.py](../src/extract/youbike.py) 的 `load_youbike()`，`parsed = parse_station(row)` 後、INSERT 前，本次實際補入：

```python
if row["sno"] in existing:
    db_row = existing[row["sno"]]
    db_values = db_row[1:]
    if db_values != parsed:
        raise ValueError("DB and parsed data not match")
    if db_row[0] != batch_id:
        raise ValueError("DB and raw batch_id not match")
    continue
```

先確認該站存在，才用 `existing[...]` 取值。同 station_id 只表示找到同站，仍須比較來源十欄與 batch。tuple 可一次比較所有欄位；不同就報錯，若需要指出哪一欄不同才另做逐欄診斷。全部相同才 `continue` 跳過本輪後面的 INSERT。站點不存在時不進這個 if，繼續執行原 INSERT。`id`、`ingested_at` 不在來源欄位比較內；採樣時間已由查詢的 `WHERE fetched_start_at = %s` 限定。

**為什麼 existing 要在迴圈前建立，且這輪不更新？**

它代表「本次載入開始前，DB 已有哪些資料」。假設載入前沒有 S001，但同一份 raw 出現兩筆 S001：第一筆 INSERT 後，existing 仍沒有 S001，第二筆會再次 INSERT，由既有 SQL 唯一約束拒絕並使站點交易回滾。若每列重新查 DB，或把新 INSERT 加入 existing，第二筆就可能把剛寫入的第一筆誤認為以前已載入而跳過。下一次重新呼叫 loader 時才重新查 DB、建立新的 existing，讓正常重播略過相同資料。

**驗證範圍**：本次側對話已做全檔語法及實際比較區塊的離線檢查：同內容同 batch 跳過、來源異值報錯、batch 不同報錯、站點不存在往下執行。未操作 DB，不據此宣稱 D4.A 整體驗收通過。本節是單次指定補記，不推進每週完整審視截止。

**後續補充（2026-10-01，間接來源 [Q-20261001-youbike-d4-a-fetchall-shape](../../question_memory/entries/Q-20261001-youbike-d4-a-fetchall-shape.md)）**：`fetchall()` 沒有符合的列時回傳空 list `[]`，不是 `None`，所以 `if rows is not None` 不能用來判斷「有沒有找到」；要寫 `if rows:`（有列才為真）或檢查 `len(rows)`。`fetchone()` 才是沒有列時回 `None`。同一次實測還看到：查詢從 `fetchone()` 改成 `fetchall()` 後，下面仍用單列 tuple 的索引去比欄位，出現 `ValueError`，因為 list of tuple 和單一 tuple 的形狀不同。

**一句話記法**：先用站點 ID 找 DB 整列，再把 DB 的來源 tuple 和 parsed 比較；existing 固定保存載入前的資料。

## KH-011：本機 HTTP 測試流程：Thread → GET → do_GET → 回應

**問題來源**：2026-10-04 本次側對話可見問答：`target=server.serve_forever` 是什麼、是否為固定啟動 thread 的函式、`send_response`／`end_headers` 的用途，以及 GET 究竟由誰、何時呼叫。Andrew 明確要求將這段 flow 的 know-how 寫入重點筆記。

**為何收錄**：服務開始等待、client 發出請求、handler 處理請求是不同步驟；分清楚才能知道程式何時執行到哪一行。

**白話重點：誰負責什麼？**

| 角色／方法 | 功用 | 何時執行 |
|---|---|---|
| `Thread(target=某個函式)` | 建立 thread 物件，指定工作 | 準備階段；尚未啟動工作 |
| `thread.start()` | 啟動另一條執行緒，讓它執行指定工作 | fixture 準備服務時 |
| `server.serve_forever()` | 持續等待、處理請求，直到要求停止 | 此例由背景 thread 執行；本身不會建立 thread |
| `requests.get(url, ...)` | client 向 URL 發出 HTTP GET | 測試呼叫產品，產品執行到這一行時 |
| `Handler.do_GET()` | 定義服務收到 GET 後如何回應 | handler 解析出 GET 後自動呼叫；測試不用直接呼叫 |
| `self.send_response(503)` | 將 503 狀態列及基本標頭放入內部緩衝區 | `do_GET()` 處理請求時 |
| `self.end_headers()` | 加入標頭結束的空白行，將緩衝標頭送出 | 回應標頭準備完成後 |

`self` 是正在處理這次請求的 handler 實例；`send_response` 和 `end_headers` 是它從 `BaseHTTPRequestHandler` 繼承的方法。GET 對應的方法名稱必須是 **`do_GET`**，不是任意命名的 `GET`。方法分派及標頭行為見 [Python HTTP server 文件](https://docs.python.org/3/library/http.server.html#http.server.BaseHTTPRequestHandler)。

**完整流程（本次討論的設計）**：

```text
pytest 準備 local_server fixture
  → 建立 HTTPServer，綁定本機位址與 port
  → 建立 Thread，指定工作為 server.serve_forever
  → thread.start()：背景開始處理請求
  → fixture 用 yield 把本機 URL 交給測試

測試呼叫 extract_youbike(url=本機 URL)
  → 產品內部 requests.get(...) 發出 GET
  → 本機服務收到請求，handler 辨識出 GET
  → 自動呼叫 Handler.do_GET()
  → send_response(503) 準備狀態與基本標頭
  → end_headers() 結束並送出標頭
  → 產品收到狀態碼 503，依自己的非 200 判斷拋出例外
  → pytest.raises 檢查產品例外與訊息

測試結束（通過或失敗）
  → fixture 繼續執行 yield 後的清理
  → server.shutdown() 停止服務迴圈
  → thread.join() 等待背景執行緒結束
  → 離開 HTTPServer 的 with 區塊，關閉 server socket
```

`thread.start()` 不會替 client 發出 GET；在這個流程中，真正發出 GET 的是產品裡的 `requests.get()`。`serve_forever` 若直接在測試所在的執行緒執行，會持續占住流程，因此才安排背景 thread，讓測試能繼續呼叫產品。[Python server 生命週期文件](https://docs.python.org/3/library/socketserver.html#socketserver.BaseServer.serve_forever)

**短語法：target 可以換，傳入函式時不加括號。**

```python
from threading import Thread

def say_hello():
    print("你好")

worker = Thread(target=say_hello)  # 指定工作，還沒執行
worker.start()                    # 在另一條執行緒執行 say_hello()
worker.join()                     # 等它完成
```

`target=say_hello` 傳入函式本身；`target=say_hello()` 則會先在目前執行緒呼叫函式，再把回傳值傳給 target。換成 `serve_forever()` 時，這個提前呼叫會一直等待／處理請求，Thread 建立流程便無法繼續。`start()` 是啟動方法；`target` 是要做的工作，不固定為 `serve_forever`。[Python Thread 文件](https://docs.python.org/3/library/threading.html#threading.Thread)

**容易搞混**：

- HTTP 狀態碼、headers、body 是不同部分。503 是狀態碼，不是 body；`end_headers()` 表示標頭結束，既不代表關閉 server，也不會自動提供 body。
- 本機服務提供 503；`Request failed with status code: 503` 是產品依收到的狀態碼產生的例外訊息；pytest 負責檢查它。
- 此設計驗證「產品收到 503 時如何處理」，不保證官方故障時一定回 503；與 [KH-001](#kh-001mock-與真實測試各自能證明什麼) 的證據界線相同。

**在專案哪裡用**：[test_youbike_extract.py](../tests/unit/test_youbike_extract.py) 的本機 HTTP fixture／503 測試，以及 [youbike.py](../src/extract/youbike.py) 的 `extract_youbike()`。本節記錄流程與 API 用法，不代表目前草稿已符合流程或正式測試已 PASS；本次未修改程式、未啟動服務、未執行產品測試，也不推進每週完整審視截止。

**一句話記法**：start 啟動服務工作，requests.get 發請求，do_GET 接招，end_headers 送完標頭，pytest 驗證產品反應。

## KH-012：Airflow 固定介面：建立 policy 物件、呼叫 evaluate 與參數 flow

**問題來源**：2026-10-07 本次側對話可見問答：RetryPolicy 寫在哪裡、次數是否要自行計算、傳 class 還是物件、建立物件是否自動執行方法，以及 op_kwargs 與 evaluate 的參數如何傳入。Andrew 最後以「框架有固定方法名與參數介面」確認理解，並明確要求寫入重點筆記。

**為何收錄**：分清楚「建立物件」「框架呼叫方法」「傳入參數」三個動作，才能理解 Airflow 並非猜測函式用途，而是依事先約定的介面執行。

**白話重點：建立物件，不等於執行所有方法。**

- `SomePolicy` 是類別；`SomePolicy()` 建立物件，通常執行 `__init__()` 初始化。
- 建立物件時不會自動執行 `evaluate()`，也不會把 class 裡的其他方法輪流執行。
- 把物件交給 operator 的 `retry_policy`，是讓 Airflow 保存並使用它；task 拋錯後，Airflow 的 worker 才明確呼叫它的 `evaluate()`。
- Airflow 約定方法名為 `evaluate`，並以具名參數呼叫。實作應保留官方介面：`evaluate(self, exception, try_number, max_tries, context=None)`；任意改掉接收的參數名稱會造成不相容。`self` 是 Python 慣例名稱，不是 Airflow 指定的 keyword。
- 其他自訂方法的名稱與參數由你決定；若需要，由你的 `evaluate()` 明確呼叫。固定介面只保證能相容呼叫，不保證你的判斷邏輯正確。

**兩條參數路徑：只有產品呼叫使用 op_kwargs。**

| operator 設定 | 交出什麼 | 何時呼叫、參數從哪來 |
|---|---|---|
| `python_callable` | 工作函式本身，不先加括號執行 | task 開始時呼叫；本次自訂業務參數由 `op_kwargs` 明確提供 |
| `op_kwargs` | 傳給上述工作函式的 dictionary | key 對應函式參數名，value 是傳入值；不負責 policy 的參數 |
| `retry_policy` | policy 類別建立的物件 | task 拋錯後呼叫其 `evaluate`；錯誤、次數與 context 由 Airflow 提供 |

若 `python_callable` 指定產品函式，`op_kwargs` 直接傳給產品；若指定接線函式，先傳給接線函式，再由它整理資料並呼叫產品。**不需要第二份 op_kwargs，也不要在建立 policy 物件時填入尚未發生的錯誤與嘗試次數。**PythonOperator 也能注入 Airflow 執行 context；這不代表框架會猜測任意業務參數的值。

**evaluate 收到的資料來源**：

| 參數 | 來源與用途 |
|---|---|
| `self` | Python 自動帶入目前的 policy 物件 |
| `exception` | Airflow 捕捉到的 task 錯誤物件，可檢查型別與附帶資訊 |
| `try_number` | Airflow task instance 記錄的目前嘗試次數；從 1 開始 |
| `max_tries` | Airflow 內部執行資訊中的嘗試上限欄位；不要自行加一或假定等於設定值 |
| `context` | 框架提供的執行相關資訊，介面允許為 None |

不需要的參數可以保留但不使用。`retries=4` 表示一般一次 task 執行允許首次加 4 次重試，最多 5 次；由 Airflow 維護計數與判斷剩餘額度，不必自行寫計數器、重試迴圈或 sleep。`RetryDecision.retry()` 允許再試但不突破額度；`RetryDecision.fail()` 立即停止；`default()` 則交回一般重試邏輯。

**可執行的小例子：把框架內部的傳值動作攤開。**

以下是普通 Python 的機制示範。`run_task` 代表框架角色，示範文字轉成年齡時出錯的呼叫流程；不是完整 Airflow 執行器或重試實作。

```python
class DemoPolicy:
    def __init__(self):
        print("① 建立 policy 物件")

    def evaluate(self, exception, try_number, max_tries, context=None):
        print("④ 執行 evaluate")
        print("錯誤類型：", type(exception).__name__)
        print("目前次數：", try_number)
        print("上限資訊：", max_tries)
        print("執行資訊：", context)

    def other_method(self):
        print("沒人呼叫這個方法，所以不會執行")


def parse_age(text):
    print("③ parse_age 收到：", text)
    return int(text)


def run_task(function, arguments, policy):
    print("② 開始執行工作")
    try:
        function(**arguments)
    except Exception as caught_error:
        policy.evaluate(
            exception=caught_error,
            try_number=1,
            max_tries=3,
            context={"task_id": "age_demo"},
        )


policy_object = DemoPolicy()
run_task(parse_age, {"text": "abc"}, policy_object)
```

從最後兩行往上追：建立 policy → 把函式、dictionary、物件交給 run_task → `**arguments` 展開成 `text="abc"` → `int("abc")` 拋出 ValueError → except 用 `caught_error` 接住 → run_task 明確呼叫 `policy.evaluate(...)`。輸出順序為 ①②③④，接著顯示 ValueError、1、3 與 context；不會印出 other_method 的內容。例中的 1、3 是為了看清傳值而寫入的示範數字；真正的 Airflow 從內建紀錄提供，不需你自行建立這些計數。

**完整 flow**：

```text
準備 DAG：
  工作函式本身 ───────────────→ python_callable
  自訂業務參數 dictionary ────→ op_kwargs
  建立 policy 物件 ───────────→ retry_policy（尚未執行 evaluate）

執行 task：
  Airflow 呼叫工作函式，傳入 op_kwargs
    → 產品正常完成：success
    → 產品拋出錯誤：Airflow 捕捉錯誤物件
        錯誤物件 ─────────────→ evaluate 的 exception
        task instance 次數 ──→ evaluate 的 try_number
        內部上限資訊 ────────→ evaluate 的 max_tries
        執行 context ────────→ evaluate 的 context
      → worker 明確呼叫 policy.evaluate(...)
      → 收到 RetryDecision
      → FAIL：直接 failed
      → RETRY：Airflow 檢查額度；可再試則安排等待與下一次執行
```

**問題來源**：2026-10-24 本次側邊對話，Andrew追問「在參數列加入existing_raw是什麼意思」「fixture是否自動取得另一個fixture」「pytest怎麼知道fixture放在第幾個argument」，並明確要求寫入筆記。

**白話重點**：pytest讀取測試函式需要的參數名稱，找出同名fixture，執行fixture取得結果，再把結果傳給測試。負責準備與傳值的是pytest；一般Python函式不會因為參數名稱相同，就自動尋找另一個函式執行，import也不會自動完成這件事。

**在現有程式哪裡用**：[test_youbike_scheduling.py](/Users/andrew/Desktop/andrew/Data_engineer/Youbike/tests/unit/test_youbike_scheduling.py)。以下名稱都來自該檔：

| 宣告 | pytest提供給該參數的值 |
|---|---|
| `existing_raw(youbike_test_env)` | 將`youbike_test_env`在`yield conn`交出的資料庫連線，傳給`existing_raw`的同名參數 |
| `controlled_raw_http_server(existing_raw)` | 將`existing_raw`回傳的字典，傳給HTTP fixture的同名參數，供它取出body |
| 測試函式參數中的`existing_raw` | 將fixture回傳的字典傳入測試；這個區域變數已經是資料，不是待呼叫的fixture函式 |

**fixture也能要求其他fixture**：pytest會沿著依賴關係先準備被需要的fixture。以`existing_raw`為例：

```text
測試要求 existing_raw
  → pytest發現 existing_raw 還需要 youbike_test_env
  → 執行 youbike_test_env，取得 yield 的 conn
  → 把 conn 傳給 existing_raw 的 youbike_test_env 參數
  → 執行 existing_raw，取得 return 的字典
  → 把字典傳給測試的 existing_raw 參數
```

**為什麼不必指定第幾個argument？** pytest按名稱準備值，再透過關鍵字參數呼叫測試。以下只示意傳參數機制，不是要求新增的程式：

```python
# raw_data代表fixture回傳的字典；conn代表fixture提供的連線。
test_existing_raw_replays_without_http(
    existing_raw=raw_data,
    youbike_test_env=conn,
)
```

`existing_raw=raw_data`明確指定要把`raw_data`交給名叫`existing_raw`的參數，因此不用靠第一個、第二個位置配對。測試函式的參數順序調換後，只要名稱仍正確，值就仍會傳給對應參數。這不表示參數排列順序決定fixture執行順序；需要先完成的準備工作應透過fixture依賴表達。

**argument實際收到什麼？** 參數列寫fixture名稱，是向pytest要求它提供的值；傳進去的不是那個fixture函式物件。即使fixture依賴另一個fixture，也是一樣的規則：

| 提供者交出的值 | 接收者的參數 | 實際收到的物件 |
|---|---|---|
| `youbike_test_env`的`yield conn` | `existing_raw`裡的`youbike_test_env` | 資料庫連線`conn` |
| `existing_raw`的`return dict` | HTTP fixture或測試裡的`existing_raw` | 含`batch_id`、`fetched_start_at`、`body`的dict |
| HTTP fixture的`yield control` | 測試裡的`controlled_raw_http_server` | 含URL、計數與Event的控制dict |

例如現有程式的開頭：

```python
@pytest.fixture
def existing_raw(youbike_test_env):
    conn = youbike_test_env
```

這裡參數雖然叫`youbike_test_env`，裡面已經是pytest傳入的連線；不是要在函式內再執行`youbike_test_env()`。

**同名函式與參數：為什麼此例不用`()`？** 模組上方的`existing_raw`名稱指向fixture提供者；測試函式宣告的同名參數，則指向pytest傳入的dict。兩處名稱相同，綁定的物件不同。原函式沒有變成dict，也沒有被永久改寫。

你目前測試的開頭是：

```python
def test_two_youbike_workers_enter_at_same_time(
    controlled_raw_http_server, youbike_test_env, existing_raw
):
    dict = existing_raw
```

進入這個函式時，pytest已完成fixture的準備，將`return dict`交出的字典傳給`existing_raw`參數。Python在函式內優先讀取自己的參數，所以右側的`existing_raw`已經是資料：

```python
dict = existing_raw    # 取得參數裡的字典，交給左邊變數
dict = existing_raw()  # 嘗試呼叫那份字典，產生TypeError
```

兩行是取值與錯誤呼叫的對照，不要把第二行放回測試。左邊變數叫`dict`或其他名稱，不影響這個錯誤；問題是右邊現在指向dict。加括號不會讓Python跳過同名參數、改去找外面的fixture函式。

一般「呼叫函式、再接回傳值」的想法沒有錯；這裡是pytest已先替你完成提供者的呼叫。能否再加`()`取決於收到的物件是否可呼叫；本例回傳dict，因此不能呼叫它。不能把這件事記成「看到fixture就一律省略括號」。

**編輯器顯示未使用，pytest還會準備嗎？** 會。未使用參數提示通常只表示測試本體沒有直接讀取該名稱；pytest仍會依參數名稱準備被要求的fixture。此外，現有依賴鏈是測試→HTTP fixture→`existing_raw`→`youbike_test_env`，所以即使測試不直接列出`youbike_test_env`，它仍會因間接依賴被準備。`existing_raw`內的`conn = youbike_test_env`也確實讀取了該連線。

同一測試依目前預設scope重複要求同一fixture時，pytest會沿用已準備的結果，不因直接與間接兩條要求就重開一份連線。若測試需要自己用`conn`查SQL，仍須在自己的參數列要求它。只有直接或間接被要求的fixture才會準備；不是所有定義過的fixture都會自動執行。一般由你自行呼叫的helper，也不會因參數同名而自動取得fixture。

### 1. 先分清楚四個執行角色

| 角色 | 在哪裡執行 | 會做什麼 | 可能停在哪裡 |
|---|---|---|---|
| pytest主執行緒 | pytest程序內 | 準備fixture、執行測試、啟動A／B、呼叫Event的clear／set／wait、收尾 | 自己呼叫的`received.wait()`、程序等待、`thread.join()`等位置 |
| HTTP服務執行緒 | 同一個pytest程序內，由`Thread`啟動 | 執行`server.serve_forever`，接到GET後執行`do_GET` | `control["release"].wait(timeout=5)` |
| A子程序 | 第一個`Popen`啟動的獨立Python程序 | worker入口→產品→取得資料庫鎖→發GET→保存與載入 | HTTP服務尚未回應時，停在產品的HTTP讀取過程 |
| B子程序 | 第二個`Popen`啟動的另一個Python程序 | worker入口→產品→嘗試取得相同資料庫鎖 | 正確的同slot路徑是拿不到鎖就退出，不等Event、不發GET |

A、B是兩個**程序（process）**，不是fixture建立的HTTP執行緒。pytest主執行緒與HTTP服務執行緒，才是同一程序內的兩條執行緒（thread）。這張表未列資料庫服務自身的程序，因為此處主要追蹤Python端的呼叫。

`control`字典與其中兩個`threading.Event`留在pytest程序內，由主執行緒和HTTP服務執行緒共用。測試收到的`controlled_raw_http_server`參數，就是fixture的`yield control`交出的同一份字典；`control = controlled_raw_http_server`只是再取一個名稱，不會複製Event或重新執行fixture。

A、B透過命令列收到URL、slot與now字串，**沒有收到這兩個Event**。所以「A等release」只是簡稱；精確說法是：**HTTP執行緒等release；A因為HTTP執行緒還沒回應，所以等HTTP。**

### 2. received、release與資料庫鎖是三個不同的東西

| 名稱／機制 | 誰改變它 | 誰觀察／等待它 | 表達什麼 |
|---|---|---|---|
| `control["received"]`，一個Event | HTTP執行緒在`do_GET`內呼叫`set()` | pytest主執行緒呼叫`wait()` | 「服務已經收到GET」；不是「A已收到response」 |
| `control["release"]`，另一個Event | fixture準備時、測試本體、fixture收尾可呼叫`set()`；本測試在啟動A前呼叫`clear()` | HTTP執行緒在`do_GET`內呼叫`wait()` | 「現在允許送出HTTP回應嗎？」 |
| PostgreSQL advisory lock | 產品透過SQL向資料庫取得／釋放 | A、B各自呼叫`pg_try_advisory_lock` | 同來源、同slot的工作，只有取得鎖者能走後續路徑 |

兩個Event互相獨立：`received.set()`不會順便把`release`設為True。`release.set()`也不會釋放PostgreSQL鎖。**Event協調測試時機，資料庫鎖實作產品的互斥。**

### 3. Event不是用一次就消失的通行證

`Event()`剛建立時內部旗標為False。以下API中的True／False是旗標狀態，不能和方法本身的回傳值混為一談：

| 呼叫 | 狀態／效果 | 呼叫者會等待嗎？ | 回傳 |
|---|---|---|---|
| `event.clear()` | 將旗標設為False，之後的wait需等待 | 不會因等待訊號而停住 | `None` |
| `event.set()` | 將旗標設為True，喚醒所有等待同一Event的執行緒 | 不等待那些執行緒完成 | `None` |
| `event.wait(timeout=5)` | True時可繼續；False時等set或逾時 | 只讓執行這次wait的執行緒等待 | 收到訊號為`True`；等到逾時仍未收到為`False` |
| `event.is_set()` | 讀取目前旗標，不改變它 | 不等待訊號 | `bool` |

同一Event若有兩個等待者，一次`set()`會使兩個都能繼續；第一個通過不會消耗旗標，也不會自動clear。之後才呼叫wait者，只要旗標仍為True，也會直接通過。「都能繼續」不保證在同一瞬間執行，實際先後由系統安排。[Python Event官方說明](https://docs.python.org/3/library/threading.html#event-objects)

這和Lock／Semaphore不同：Lock一次只允許一個持有者；Semaphore用名額計數，取得名額會扣除。Event沒有「拿走一個名額」的動作。**deadlock是互相等待而無法前進的狀態，不是一種規定每次只能救一人的工具。**

### 4. 為什麼fixture一開始set，A後來仍然會等？

現有fixture準備階段包含：

```python
control = {"get_count": 0, "received": Event(), "release": Event()}
control["release"].set()
```

這時release確實為True，但A尚未啟動，沒有等待者要被放行。它只是設定這個服務預設可以立即回應。接著fixture啟動HTTP服務執行緒，執行到`yield control`把字典交給測試。

測試本體後來執行：

```python
control["release"].clear()
start_youbike_worker(control["url"], slot, slot)
```

clear先把**同一個Event**改回False，才啟動A。所以A的GET到達後，HTTP執行緒讀到的是False，仍然要等。最初那次set不是永久許可，也不是先存一張永遠可用的票。

| 時點 | 執行者／動作 | release旗標 | A的狀態 |
|---|---|---|---|
| 1 | pytest準備fixture，建立Event | False | 尚未存在 |
| 2 | fixture準備階段呼叫`release.set()` | True | 尚未存在 |
| 3 | fixture啟動HTTP執行緒、`yield control` | True | 尚未存在 |
| 4 | pytest進入測試，呼叫`release.clear()` | False | 尚未存在 |
| 5 | pytest呼叫helper啟動A | False | 開始執行worker |
| 6 | A發GET，HTTP執行緒執行`release.wait()` | False | 等待HTTP回應 |

**clear本身不會卡住fixture，也不會把所有執行緒凍結。** 它只改旗標；HTTP執行緒要實際走到wait，才會因False等待。此時主執行緒仍可繼續工作。

### 5. 誰呼叫誰？從啟動A一路走到等待

```text
pytest主執行緒
  → 呼叫 start_youbike_worker(url, slot, now)
  → helper建立 subprocess.Popen(...)
  → 系統啟動A子程序；helper回傳Popen物件，pytest可往下走

A子程序（和pytest分開執行）
  → 執行 youbike_worker.py 的 main()
  → parse_args()取得URL、slot、now
  → set_worker_clock(now)設定此程序內產品看到的時間
  → extract_youbike(url=url, scrape_time=slot)
  → 取得該slot的PostgreSQL鎖
  → 確認此slot沒有raw，且未過期
  → requests.get(url, ...)向本機服務發出GET
  → 等待服務回應

HTTP服務執行緒
  → serve_forever處理抵達的GET
  → HTTP handler呼叫 do_GET()
  → get_count加1
  → received.set()：通知pytest「GET到了」
  → release.wait(timeout=5)：False，因此暫停在這裡
  → 尚未執行send_response／end_headers／wfile.write
```

**Popen啟動程序，不等待整個爬蟲完成才回傳。** helper的return只表示把程序控制物件交回pytest；不表示A已經完成。A、pytest、HTTP執行緒之後各自走自己的流程。傳入now等於slot，是讓這個歷史測試slot在worker眼中尚未過期；不需要在此另爬一次或改產品流程。

### 6. assert為什麼能通過，然後主程式繼續啟動B？

主執行緒的這一行：

```python
assert control["received"].wait(timeout=5)
```

等待的是received，不是release，也不是「等A結束」。HTTP執行緒已先執行`received.set()`，所以主執行緒的wait會回傳True，assert通過，主執行緒就能執行下一行啟動B。

收到訊號當下，HTTP執行緒可能正要進入release.wait，也可能已經停在其中；因為release仍為False，它無法正常往下送200回應。**received先set、release再wait的順序，讓主程式知道A已到達，又能維持A尚未完成。**

```text
HTTP執行緒：received.set() ──通知──→ 主執行緒：received.wait()回傳True
      │                                      │
      ↓                                      ↓
release.wait()等待主程式放行                  assert通過，啟動B
      │
      └── 尚未送response，所以A仍等HTTP
```

B沒有跳過assert，也沒有先於A偷偷執行；**pytest已通過自己的assert，才呼叫第二次helper啟動B。** 不需要先把release設為True才有能力執行B。

### 7. B進來後，誰會卡住？誰不需要別人救？

前提是A仍在上述HTTP等待階段，且B收到相同slot。產品已讓A持有該slot的資料庫鎖。B執行到現有程式：

```python
cursor.execute("SELECT pg_try_advisory_lock(%s, %s)", slot_key)
if cursor.fetchone()[0] == False:
    logger = logging.getLogger(__name__)
    logger.warning(f"Another process is already running for slot {slot_key}. Exiting.")
    return
```

`pg_try_advisory_lock`拿不到時**立即回傳False，不等待A解鎖**。產品return後，worker的main也結束，B正常退出；沒有拋出錯誤時通常退出碼為0。B不會走到requests.get，所以不會進HTTP handler，更不會直接等待release。[PostgreSQL advisory lock官方說明](https://www.postgresql.org/docs/current/functions-admin.html#FUNCTIONS-ADVISORY-LOCKS)

此刻的關係應是：

| 角色 | 狀態 | 等誰／需誰做什麼 |
|---|---|---|
| 主執行緒 | 可等待B結果並核對A仍未結束 | B不等release，因此能在放行A之前結束 |
| HTTP執行緒 | 等`release.wait()` | 主執行緒呼叫release.set |
| A | 等HTTP回應，仍持有資料庫鎖 | HTTP執行緒送出回應 |
| B | 拿不到資料庫鎖，直接return並退出 | 不需要任何人解鎖或set來「救」它 |

產品的鎖是session層級。A離開查詢用cursor，不等於釋放鎖；同一連線仍開著，鎖會跨過HTTP等待及raw寫入，正常完成後才明確unlock，連線結束也會釋放該session持有的鎖。

### 8. 主程式呼叫release.set，到底「救」到誰？

應分成兩段理解，不能說成「A直接收到Event」：

```text
主執行緒呼叫 control["release"].set()
  → 直接讓HTTP執行緒的release.wait回傳True
  → HTTP執行緒往下準備200、送headers、寫body
  → A收到HTTP回應與body，才能繼續保存raw、載入站點
  → A正常路徑釋放PostgreSQL鎖，結束產品與worker
  → 主執行緒等待A的操作才會完成
```

所以：**主程式用set直接放行HTTP執行緒；HTTP執行緒用response間接讓A繼續；A最後自己釋放資料庫鎖。** B在正確路徑已退出，不需要第二次set。

即使假設另有多個執行緒等待同一release，一次set也會放行所有等待者。不過目前使用的是`HTTPServer`，不是`ThreadingHTTPServer`，只有一條背景HTTP執行緒逐一處理請求；不要把「Event能喚醒所有等待者」誤認成「這個server本來就同時處理多個GET」。若產品失去排他保護，B的GET可能先在連線佇列等待，單看當下get_count等於1仍不足以證明保護正確。[Python HTTPServer說明](https://docs.python.org/3/library/http.server.html#http.server.HTTPServer)

### 9. 完整的目標時序：重疊不是同一毫秒開始

以下是前述測試設計要觀察的順序，**不代表目前存檔已完成所有等待及結果檢查**：

| 順序 | 主執行緒 | HTTP執行緒 | A子程序 | B子程序 |
|---|---|---|---|---|
| 1 | 準備fixture，取得control | 已啟動，等GET | 尚未啟動 | 尚未啟動 |
| 2 | release.clear，啟動A | 等GET | 開始產品工作 | 尚未啟動 |
| 3 | 等received | 收到A的GET，received.set，等release | 已持有鎖，等HTTP回應 | 尚未啟動 |
| 4 | received.wait回傳True，啟動B | 仍等release | 仍等HTTP回應 | 開始工作 |
| 5 | 等B退出並核對成功、A仍未結束 | 仍等release | 仍未完成、仍持鎖 | try-lock拿不到，直接退出 |
| 6 | release.set | wait回傳True，送回應 | 收到回應，往下處理 | 已結束 |
| 7 | 等A結果，再查既定HTTP／DB結果 | 完成這次GET | 正常完成並釋放鎖 | 已結束 |
| 8 | 測試結束，收回程序與fixture | 結束服務迴圈 | 已結束或被清理 | 已結束或被清理 |

這裡要證明的是**B進入及退出時，A仍在執行**，不是A、B必須同一毫秒啟動。先讓A到達HTTP等待點，是為了明確建立「A已持鎖且未完成」，再觀察B能否正確退出。

### 10. 早期存檔的第二次received.wait，並不是「等B到了」

2026-10-25較早寫本節時，第一個測試的相關原碼如下；之後已移除第二次wait並補上A／B程序等待與退出碼，以下保留為曾經出錯的原因，不是現行待辦：

```python
control["release"].clear()
start_youbike_worker(control["url"], slot, slot)
assert control["received"].wait(timeout=5)
start_youbike_worker(control["url"], slot, slot)
assert control["received"].wait(timeout=5)
control["release"].set()
```

第一個received.wait可以等到A的GET。但A的handler已把received設成True，程式中沒有再次clear；因此第二個received.wait會沿用A留下的True，直接通過，**不表示B已進入產品、不表示收到第二個GET，也不表示B已退出**。Event是狀態旗標，不會自動替每個worker記一次新到達。

主執行緒可能剛建立B，就立刻通過第二次wait並放行A；B可能還在啟動Python與import模組。此時A有機會先完成，B後來才進產品，便不能保證測到了兩者重疊。這是目前原碼可看出的觀察缺口，不是本次實跑發現的FAIL。

把received再clear也不是用來等B的正確到達訊號：**預期B應在HTTP之前退出，本來就不該讓handler再次set received。** 前述設計用B的程序結束結果，以及放行前A仍未結束的觀察，建立需要的證據；不是再等一次相同HTTP訊號。本次只記錄解釋，沒有替換這段正式測試。

### 11. fixture不再初始化，為什麼do_GET後來還會執行？

fixture準備階段做的是「定義handler類別、建立server、啟動服務執行緒」。定義`def do_GET`時不會執行其函式本體；之後有GET抵達，已運行的server才透過handler呼叫它。

因此要分清三個時機：

| 時機 | 執行內容 | 是否因每次GET而重做 |
|---|---|---|
| fixture準備 | 建立control、最初release.set、啟動HTTP執行緒、yield | 否；本測試沿用已準備的fixture |
| 每次GET | handler執行do_GET內的計數、received.set、release.wait及回應 | 是，只有真的進入handler處理GET時 |
| fixture收尾 | yield之後的finally：release.set、停止server、join | 否；測試正常返回或拋錯結束後才收尾 |

fixture的generator暫停在yield，不代表HTTP執行緒也暫停。helper也不會因為啟動A／B就重新執行fixture。測試結束時pytest才恢復yield後的清理，**不是每發一個GET就執行一次finally**。[pytest yield fixture說明](https://docs.pytest.org/en/stable/how-to/fixtures.html#teardown-cleanup-aka-fixture-finalization)

目前finally中set後的註解`next time requests initiate`容易誤導；此位置的實際用途是收尾時讓可能等待中的handler能繼續，以便結束服務，不是預告下一次請求要初始化fixture。本筆記只更正解釋，未改該註解或程式。

### 12. 哪些等待順序會互相卡住？

**情況一：主程式先等A結束，卻還沒放行HTTP。**

```text
主執行緒：等A結束，之後才打算release.set
    ↓
A：等HTTP回應才能結束
    ↓
HTTP執行緒：等主執行緒release.set才送回應
    ↓
主執行緒仍在等A……形成循環
```

若沒有逾時或其他外力，這個循環無法自行前進。前述設計是在A被暫停時先觀察B，然後**先set放行HTTP，再等A完成**，切斷這個循環。

**情況二：handler先等release，卻尚未通知received。** 現有順序是received.set在前、release.wait在後。如果倒過來，主程式等received、HTTP等release，而主程式又打算等received後才release，就會互等。這也是為什麼「已收到GET」訊號必須在暫停回應之前送出。

**情況三：B改成等待資料庫鎖，而主程式正在等B。** 如果使用會等待的`pg_advisory_lock`，而不是目前的try-lock，可能形成：主程式等B→B等A的DB鎖→A等HTTP→HTTP等主程式set。現有`pg_try_advisory_lock`會回傳False讓B退出，避免讓B加入這個等待環。

這些是等待依賴的分析，不能記成「只要有Event就不會deadlock」。**要看負責發訊號的人，能不能走到set那一行。**

### 13. 逾時與收尾：沒有無限等，不代表測試成功

現有handler用`release.wait(timeout=5)`；若5秒內沒有取得放行訊號，會回傳False，handler送504後return。因此前面表格的「A持續等待」以尚未逾時為前提；不能假設旗標False就會永遠卡住。父執行緒還可能受系統排程延遲影響，數值本身不是重疊執行的證據。

主程式的`assert received.wait(timeout=5)`也有逾時：False會使assert失敗，測試拋出AssertionError，pytest接著執行已準備fixture的清理。這不是「assert永遠卡死」，也不是「等A做完」。兩個wait各自從呼叫當下計時，並非共享一個5秒計時器。

若觀察子程序，`Popen.communicate(timeout=...)`會讀取stdout／stderr並等待該程序結束；`poll()`回傳None表示目前尚未結束，結束後回傳退出碼。此helper使用PIPE，所以等結果時需同時處理輸出，不能忽略輸出緩衝區塞滿的可能。**communicate逾時只拋TimeoutExpired，不會自動終止子程序**；清理仍需收回測試自己建立而尚未結束的A／B，再完成輸出回收。這是API生命週期說明，本次沒有啟動或終止任何子程序。[Python子程序等待與清理](https://docs.python.org/3/library/subprocess.html#subprocess.Popen.communicate)

HTTP fixture現有收尾先release.set，再停止服務，最後join。先set是讓正在等release的HTTP執行緒能離開wait；停止服務則由pytest主執行緒發起，不是在serve_forever自己那條執行緒內等待自己結束。join的意思是等HTTP執行緒退出，**不會順便等A、B這兩個Popen子程序**。[Python server.shutdown生命週期](https://docs.python.org/3/library/socketserver.html#socketserver.BaseServer.shutdown)

Event逾時、HTTP逾時與finally清理可讓失敗有機會結束並回報，但不能把「最後靠逾時／清理才解開」當成正常測試流程通過。正常路徑仍須按目標時序主動放行、確認程序結果，不能只等fixture收尾代做全部工作。

### 14. 回查用的「誰通知誰」表

| 動作 | 誰呼叫 | 直接影響誰 | 不代表什麼 |
|---|---|---|---|
| `received.set()` | HTTP執行緒 | 讓主執行緒的received.wait可回傳True | 不代表已送response，不會放行release |
| `release.clear()` | 主執行緒 | 讓後續release.wait要等訊號 | 不是把主程式或整個fixture停住 |
| `release.set()` | 主執行緒；收尾時也由fixture執行 | 所有等待該Event的執行緒；本題主要是HTTP執行緒 | 不會只消耗一次、不會直接釋放DB鎖 |
| `end_headers()`／`wfile.write(body)` | HTTP執行緒 | 送HTTP回應給A，讓A的HTTP讀取往下走 | 不會替B取得DB鎖，也不代表A整份工作已完成 |
| `pg_try_advisory_lock` | A／B各自在產品內向DB請求 | DB決定該連線是否立即取得鎖 | B拿不到時不等待release |
| `pg_advisory_unlock` | A在產品正常完成路徑執行 | 釋放A持有的對應DB鎖 | 不會更動任何Event旗標 |

**一句話記法**：HTTP收到A的GET→received通知主程式→HTTP等release、A等response→主程式啟動並確認B退出→主程式set放行HTTP→HTTP回應讓A繼續→A完成後釋放DB鎖。Event負責時機，DB鎖負責互斥。

**為何收錄**：這些問題都在問「失敗時要收什麼、收多少、怎麼收」，屬原理追問，不推定他不會。同日助理自行寫注入程式去跑他的測試而被糾正分工，以及「引導以 HTML 為準」的糾正，都是流程，不是知識缺口，不收錄。

**白話重點**：

- **finally 的目的是失敗時不留下還在跑的 worker**（否則它會在測試判失敗之後，繼續寫 `youbike_test`、佔著鎖），不是「讓 A 做完」。B 卡住時看起來像「砍 B、放行 A、A 跑完」，那只是順序：先放行讓等得到的自己結束，等不到的才 `kill()`。A、B 用同一套規則。
- **收尾看失敗當下 worker 的狀態，不看哪一行 assert 失敗**：還沒啟動就跳過、已結束就不碰、還在跑才收。所以不必每個 assert 都假裝失敗一次。D11 的 HTML 現行決定節只要求「正常結果＋失敗清理證據」，並寫明正式測試維持原三情境、不新增。「B 掛掉」是兩個 worker 都可能還活著的代表性失敗，這是助理的推論，不是 HTML 原文。

| 失敗發生在 | A | B | 收尾要做的事 |
|---|---|---|---|
| A 沒到 HTTP | 在跑 | 還沒啟動 | 只處理 A |
| B 卡住或沒正常結束 | 卡在 HTTP | 卡住或已結束 | 先放行；B 沒結束就 kill |
| 放行後 A 不結束 | 卡住 | 已結束 | A 逾時就 kill |
| 結束碼、GET 次數、筆數的檢查 | 已結束 | 已結束 | 沒有東西要收 |

- **`except:` 處理完就結束，失敗被吞掉，測試反而通過。** 要嘛在 `except` 區塊最後加一個沒有參數的 `raise`（把正在處理的那個錯誤原樣再丟出去），要嘛改用 `finally`（自動往外丟）。只要加一個，放在 except 最後；assert 不必改成 raise，它失敗本來就是丟 `AssertionError`。
- **收拾和判定是兩件事**（間接來源）：`except`／`finally` 裡做的是「收拾」（砍掉卡住的 B、放行並等 A），`raise` 是「判定」（讓 pytest 知道測試失敗）。收拾好不代表通過：B 搶不到鎖就該馬上離開，B 卡住正是排他壞掉時最可能的樣子，收掉 B 並不會讓產品的問題消失，所以只有 B 錯也要讓錯誤往外丟。B 沒錯、別的檢查失敗時，收尾看的是各 worker 的狀態（兩個多半都已結束，沒有東西要收），最後同樣往外丟。裸 `except:` 會接住所有錯誤，逾時與 assert 失敗又是不同種錯誤，沒辦法用錯誤種類只挑出某個 worker 的問題，所以收尾才用 worker 的狀態判斷。
- **收尾本身不要再出新錯，也不放檢查**（間接來源）：檢查（assert）全部留在 try，`finally`／`except` 只放動作（放行、停掉、收回）。理由有二：測試通過時 `finally` 也會跑，裡面 assert 的前提（例如「某個東西還在跑」）在成功時多半不成立，會讓檢查全過的測試反而失敗；測試失敗時，收尾裡的 assert 或沒接住的 `communicate()` 逾時若又出錯，新的錯誤會蓋掉原本的失敗原因。要確認「沒有殘留的 worker」，由測試之外的驗證去查，不放在收尾裡。

**小例子**（工作代理情境，`Job` 是虛構類別；Python 3.9.6 實跑）：

```python
class Job:
    def __init__(self, name):
        self.name, self.alive = name, True

    def stop(self):
        print("  收尾：停掉", self.name)
        self.alive = False


def run(fail_at):
    a = b = None                         # 先設 None：a 還沒建立就失敗，收尾也讀得到名字
    try:
        a = Job("A")
        if fail_at == "a-step":
            raise RuntimeError("A 階段失敗")
        b = Job("B")
        if fail_at == "b-step":
            raise RuntimeError("B 階段失敗")
        a.alive = b.alive = False        # 兩個都正常做完
        if fail_at == "check":
            raise RuntimeError("最後檢查失敗")
    finally:
        for job in (a, b):
            if job is not None and job.alive:
                job.stop()
```

| `run(...)` 的參數 | 收尾印出 | 呼叫者收到 |
|---|---|---|
| `"a-step"` | 停掉 A | `A 階段失敗` |
| `"b-step"` | 停掉 A、停掉 B | `B 階段失敗` |
| `"check"` | （沒有東西要收） | `最後檢查失敗` |
| `None` | （沒有東西要收） | 沒有錯誤 |

同一個收尾，四種失敗點都走得通；差別只在 `alive` 的狀態。再看 `except` 有沒有 `raise`：

```python
def swallow():
    try:
        raise RuntimeError("中途失敗")
    except:
        print("收尾")                    # 沒有 raise：錯誤到此為止

def keep():
    try:
        raise RuntimeError("中途失敗")
    except:
        print("收尾")
        raise                            # 沒有參數：把正在處理的錯誤原樣再丟出去
```

實跑：`swallow()` 印出「收尾」後正常回來，呼叫者沒有收到任何錯誤；`keep()` 印出「收尾」後，呼叫者收到 `RuntimeError: 中途失敗`。

**在專案哪裡用**：[test_youbike_scheduling.py](../tests/unit/test_youbike_scheduling.py) 的 `test_two_youbike_workers_enter_at_same_time`。HTML 現行決定節寫的做法（建議，不是門檻）：A、B 先設 `None` → try 從啟動 A 涵蓋到最後檢查 → finally 先 `release.set()`，再收回本次已啟動且仍在跑的 worker（`communicate(timeout)`，逾時 `kill()` 後再 `communicate()`）。存檔快照只記時間點：11/01 14:44 的版本把收尾放在沒有 `raise` 的 `except:`（依對話中助理用同結構假程序的重現，B 卡住時測試仍會通過）；16:30 的版本已在收尾最後加 `raise`。存檔隨時會變，這裡不判定是否達成驗收；D11 第一個正式情境尚未通過（依 HTML：正式三情境 0/3），等 Andrew 說做好後，再依 HTML 的停止條件驗證。

**容易搞混**：

- 進了 finally（或 except）≠ 子程序被收掉：要自己 `kill()`，再 `communicate()` 回收。
- 「兩種寫法都行」的前提是目的相同：失敗照樣被回報、不留下 worker。HTML 寫 finally，是因為不必記得 `raise`。
- 單獨的 `raise` 只能用在「正在處理錯誤」的位置（`except` 區塊裡）；沒有錯誤在處理時單獨寫 `raise`，會得到 `RuntimeError: No active exception to reraise`。

**一句話記法**：assert 只負責立刻失敗；收尾看 worker 的狀態、不看哪一行 assert；用 `finally`，或 `except` 的最後記得 `raise`。

**核對與限制**：範例以 `/usr/bin/python3`（3.9.6，`-I`）在暫存區實跑；`raise` 的行為見 [Python 官方 raise 陳述式](https://docs.python.org/3/reference/simple_stmts.html#the-raise-statement)。專案內容依 HTML 與上列存檔快照；15:41 之後的追問只有 question_memory 摘要。未執行 pytest、未啟動 worker、未連 DB，不宣稱 Andrew 已獨立掌握。

## KH-016：COALESCE：由左到右取第一個非 NULL，兩個都有值時順序有差

**問題來源**（直接來源，Claude 對話）：2026-11-01 14:06，`706f92e0-5f3f-4394-910f-c01702f5b3aa.jsonl`。助理指出排他測試挑 slot 的 SQL 裡，`COALESCE` 的兩個參數順序要對調（`MIN(fetched_start_at)` 放第一個），Andrew 問：它不是「一個是 NULL 就拿另一個」嗎，為什麼要對調？前一則（14:05）助理描述他 10/27 的存檔把 `NOW()` 寫在前面；10/25 的引導原本就寫 `MIN` 在前。

**為何收錄**：他的說法在「只有一個是 NULL」時是對的；缺的一塊是「兩個都有值時，永遠拿左邊」，所以順序一換結果就換。這種寫反不會報錯，只會悄悄改變結果，值得記一張表。不推定他不懂 COALESCE。

**白話重點**：

- `COALESCE(a, b, c)` 由左往右，回傳第一個**不是 NULL** 的值；全部都是 NULL 才回 NULL。官方還寫了兩件事：右邊的參數只在需要時才計算；所有參數的型別要能轉成同一種（例如時間不能配 `0`）。[PostgreSQL COALESCE](https://www.postgresql.org/docs/16/functions-conditional.html#FUNCTIONS-COALESCE-NVL-IFNULL)
- 想表達「優先用 A，沒有 A 才用 B」→ 優先的放左邊、備援放右邊。`NOW()` 永遠不是 NULL，放在左邊，右邊的參數就永遠輪不到。
- 只跳過 `NULL`：`0`、空字串 `''` 都不是 NULL，會被當成「有值」。
- `MIN()`、`MAX()` 對沒有任何列的表回 NULL（不報錯），所以常拿來配 COALESCE 當「空表時的備援」。

**小例子**（運費情境：優惠券運費 > 會員運費 > 標準運費。下面是同規則的 Python 類比，不是 SQL；已實跑）：

```python
def coalesce(*args):
    for value in args:
        if value is not None:
            return value
    return None

coalesce(None, None, 60)   # 60：前兩個都沒有，才用標準運費
coalesce(None, 0, 60)      # 0 ：會員運費是 0（免運），不是 NULL，就用它
coalesce(30, 0, 60)        # 30：左邊先有值就停，右邊不看
coalesce(60, 30, None)     # 60：同樣的值換順序，答案就跟著變
coalesce("", None, "x")    # ''：空字串不是 None，也算有值
```

**在專案哪裡用**：[test_youbike_scheduling.py](../tests/unit/test_youbike_scheduling.py) 的 `test_two_youbike_workers_enter_at_same_time` 開頭，用 SQL 挑一個「還沒有 raw 的舊時段」：`date_trunc('hour', COALESCE(MIN(fetched_start_at), NOW()), 'UTC') - INTERVAL '60 minutes'`（11/01 16:30 存檔快照）。意思是「有 raw 就從最早那筆往前一小時，表是空的才從現在往前一小時」。兩種順序的差別，用 11/01 對話裡助理的唯讀查詢值（當時 DB 時間 06:03Z、最早的 raw 是 09/25 07:35Z）：

| 寫法 | 表裡有 raw 時 COALESCE 取到 | 挑出的時段 |
|---|---|---|
| `NOW()` 在前 | `NOW()`（11/01 06:03Z） | 11/01 05:00Z（前一個整點） |
| `MIN(...)` 在前 | 最早的 raw（09/25 07:35Z） | 09/25 06:00Z（比最早的 raw 還早） |

`NOW()` 在前時，同一小時內第二次跑會選到第一次已經寫過 raw 的同一個時段；產品看到該時段已有 raw 就走重播、不發 HTTP（`extract_youbike()` 先查 raw 再決定要不要抓），測試等不到 HTTP 請求而失敗。

**容易搞混**：

- 「一個是 NULL 就拿另一個」只描述了其中一種情況；兩個都有值時，永遠拿左邊。
- 型別要相容：`COALESCE(NULL::timestamptz, 0)` 會得到 `DatatypeMismatch`（10/25 對話中助理在 `youbike_test` 實跑），備援必須是時間。

**一句話記法**：COALESCE 由左往右，第一個不是 NULL 的就是答案；想當備援的放最右邊。

**核對與限制**：規則依 PostgreSQL 16 官方文件；例子是 Python 類比（`/usr/bin/python3` 3.9.6 實跑）。本次沒有連 DB，表中的數字是 11/01 對話裡助理取得的值，未重查。存檔內容只記時間點，不判定。

## KH-017：受控時鐘：為什麼測試要固定「現在」，時間怎麼一路傳到產品

**問題來源**：

- 間接來源（question_memory 摘要，Codex 時期，不是原文）：2026-10-20～10-24 對 worker 的時間鏈連續追問。`args.now` 長什麼樣（[Q-20261020-youbike-args-now-format](../../question_memory/entries/Q-20261020-youbike-args-now-format.md)）；誰在呼叫 `WorkerDateTime`（[Q-20261020-youbike-worker-datetime-call-site](../../question_memory/entries/Q-20261020-youbike-worker-datetime-call-site.md)）；worker 的用途與為何先格式化再解析（[Q-20261020-youbike-worker-purpose-time-transport](../../question_memory/entries/Q-20261020-youbike-worker-purpose-time-transport.md)、[Q-20261021-youbike-time-roundtrip-necessity](../../question_memory/entries/Q-20261021-youbike-time-roundtrip-necessity.md)）；`set_worker_clock` 結束後還記不記得時間、再進 `now` 會不會重設（[Q-20261021-youbike-clock-closure-retained-datetime](../../question_memory/entries/Q-20261021-youbike-clock-closure-retained-datetime.md)、[Q-20261021-youbike-clock-conversion-timing](../../question_memory/entries/Q-20261021-youbike-clock-conversion-timing.md)、[Q-20261021-youbike-now-local-vs-captured-variable](../../question_memory/entries/Q-20261021-youbike-now-local-vs-captured-variable.md)、[Q-20261021-python-closure-reference-lifetime-v3](../../question_memory/entries/Q-20261021-python-closure-reference-lifetime-v3.md)，後者要求直接用現有 worker 原碼解釋 closure）；最外層 `return` 是否必要（[Q-20261021-youbike-unused-worker-clock-return](../../question_memory/entries/Q-20261021-youbike-unused-worker-clock-return.md)）；slot 與 now 是不是兩條路（[Q-20261021-youbike-clock-override-vs-slot-format](../../question_memory/entries/Q-20261021-youbike-clock-override-vs-slot-format.md)）；以及 10/24 的「為何還要從 slot 算出固定 now」（[Q-20261024-youbike-past-empty-slot-controlled-now-purpose](../../question_memory/entries/Q-20261024-youbike-past-empty-slot-controlled-now-purpose.md)）。
- 直接來源：2026-11-01 14:01，`706f92e0-5f3f-4394-910f-c01702f5b3aa.jsonl`。Andrew 自己推論「這個做法本質上只供測試，正式環境不能把 min−60 的資料送進 DB，那是過去的」。

**為何收錄**：一週內同一條時間鏈被追問十幾次，10/24 還在問「為何需要固定 now」，屬原理追問。`set_worker_clock` 是 10/16 Andrew 明確授權由助理代寫、供閱讀理解的函式，所以這些是「讀別人寫的程式」的問題，不是他自己的實作錯誤。11/01 他自己推出「只供測試、正式不能補寫過去時段」，方向正確，顯示理解有進展；細節仍持續觀察，不宣稱已掌握。10/16 起另有「範例太大、先備不足」的教學糾正，屬引導方式，不收錄。`cls` 與 classmethod 見 [工程筆記 2026-10-16](engineering_challenges_log.md)；但該篇與同日「直接閱讀實作的受控時鐘」節描述的是舊版（classmethod、最外層 `return`），現行寫法（10/21 存檔快照）是 `@staticmethod`、沒有 `return`，以現行為準。

**白話重點**：

1. **為什麼要固定「現在」**：產品對沒有 raw 的時段，會比較「現在 ≥ 時段起點 + 30 分鐘」，成立就記 `missing`、不發 HTTP、也不寫 raw（`extract_youbike()` 的過期判斷，10/14 存檔快照）。D11 排他測試要用「沒有 raw 的舊時段」，A、B 才都會走到 HTTP 這一關；用真實的今天，舊時段一定被判過期。所以要讓產品「以為現在還在那個時段裡」。slot 本身就是時段起點，指定 `now = slot` 即可，不必加 1 分鐘。
2. **時間怎麼走**（跨程序只能傳文字）：測試用 SQL 選出 slot → 命令列 `--slot`、`--now` 兩個字串 → worker 的 `args.now`（`str`）→ `set_worker_clock` 解析成有時區的 datetime、轉 UTC，存進 `new_now` → 產品執行 `DateTime.now(timezone.utc)` 時讀到它。
3. **兩條時間路徑別混**：`slot` 走產品參數 `scrape_time`，決定「處理哪一格」；`now` 走被替換的時鐘，決定「現在幾點」。兩者在過期比較碰頭。例：slot = 09:00、指定 now = 09:31，過期線 09:30，09:31 ≥ 09:30 → 過期。
4. **三個 Python 語法點**：
   - **closure**：內層 `now` 引用外層的 `new_now`，外層函式結束後仍保留，所以 `set_worker_clock` 不需要 `return`。每次呼叫 `now` 只會建立自己的參數 `tz`，不會重設 `new_now`；解析與轉 UTC 只在安裝時做一次，每次 `now(tz)` 只做 `astimezone(tz)`。要換成另一個時間，得再呼叫一次 `set_worker_clock`。
   - **`@staticmethod`**：`now(tz=None)` 用不到 `cls`，所以用 staticmethod，產品照常以 `DateTime.now(tz)` 呼叫。
   - **換的是「產品模組裡的名字」**：`youbike_module.DateTime = WorkerDateTime`。產品在自己的模組裡找 `DateTime`，所以換這個名字就夠；標準 `datetime` 套件與其他程序不受影響。這也是產品原始碼裡看不到 `WorkerDateTime.now` 字樣、它卻會被呼叫的原因。
5. **回答 11/01 的提問**：對，只供測試。正式排程時 DAG 把 `{{ data_interval_end }}` 當 `scrape_time` 傳進來（就是當下那一格），產品用真實的 `now`；過期且沒有 raw 的時段只記 `missing`（HTTP 0 次、不寫 raw），有 raw 的時段是用已存的 raw 重播、不是重抓。DAG 也設了 `catchup=False`；HTML 的說法是「不能拿現在 snapshot 填成過去觀測」。

**小例子**（優惠券過期情境，`shop` 是虛構模組；這是機制類比，不是專案程式，Python 3.9.6 實跑）：

```python
import types
from datetime import datetime as DateTime, timezone

shop = types.ModuleType("shop")
shop.Clock = DateTime                          # 產品模組裡的「時鐘」名字

def coupon_status(deadline_iso):
    deadline = DateTime.fromisoformat(deadline_iso)
    now = shop.Clock.now(timezone.utc)         # 每次判斷才去模組裡找 Clock
    return "過期" if now >= deadline else "可用"

def install_fixed_clock(text):
    fixed = DateTime.fromisoformat(text.replace("Z", "+00:00")).astimezone(timezone.utc)

    class FixedClock(DateTime):
        @staticmethod
        def now(tz=None):
            if tz is None:
                return fixed.astimezone().replace(tzinfo=None)
            return fixed.astimezone(tz)        # fixed 來自外層函式，每次呼叫都讀同一個

    shop.Clock = FixedClock                    # 只換 shop 模組裡的名字

deadline = "2040-01-01T09:30:00+00:00"
coupon_status(deadline)                        # '可用'（真實現在是 2026 年）
install_fixed_clock("2040-01-01T09:31:00Z")
coupon_status(deadline)                        # '過期'
```

實跑結果：

- 換之前是「可用」；固定成 09:31Z 之後是「過期」。
- `shop.Clock.now(timezone.utc)` 連續呼叫兩次，都得到同一個 `2040-01-01 09:31:00+00:00`（closure 保留 `fixed`，沒有重設）。
- 標準 `DateTime.now(timezone.utc)` 的年份仍是 2026：只換了 `shop` 模組裡的名字。
- 再呼叫一次 `install_fixed_clock("2040-01-01T09:10:00+02:00")`，換成 `07:10:00+00:00`；`install_fixed_clock` 沒有 `return`（回傳 `None`），時鐘照樣生效。

**在專案哪裡用**（存檔快照會變，只記時間點）：

- [youbike_worker.py](../tests/helpers/youbike_worker.py)（10/21 14:32 存檔）的 `set_worker_clock`、`main`。
- [youbike.py](../src/extract/youbike.py)（10/14 15:27 存檔）的 `extract_youbike()`：`scrape_time` → `request_time`，以及「沒有 raw 時比較現在與過期線」。
- [test_youbike_scheduling.py](../tests/unit/test_youbike_scheduling.py)（11/01 16:30 存檔）的 `start_youbike_worker`（以 `--slot`、`--now` 開 Popen）；第一個測試把同一個 `slot` 當作 `--slot` 與 `--now`。

**容易搞混**：

- 「格式化再解析」不是多此一舉：命令列只能傳文字，worker 要 datetime 才能 `astimezone`；同一個程序內直接呼叫產品時，不必再 `isoformat`（10/21 釐清）。
- 固定 now 不是等待或睡眠，也沒有讓時間流動；它只讓產品在「現在 = 指定值」時走對應的分支。
- 不帶時區的分支 `astimezone().replace(tzinfo=None)`，是轉成執行程序的本機時區再拿掉時區標記（本機台北：09:10Z → 17:10）；產品傳 `timezone.utc`，不會走這個分支。
- 受控時鐘不等於真實排程：它只證明「產品在現在 = 指定值時的分支行為」。

**一句話記法**：slot 決定處理哪一格，now 決定現在幾點；測試選舊 slot，就要把 now 也拉回那一格，產品才不會判過期。

**核對與限制**：事實對照上列存檔快照（隨時會變，不當標準答案）與 HTML D11 現行決定；Python 範例以 `/usr/bin/python3`（3.9.6，`-I`）在暫存區實跑；Codex 時期問答只有 question_memory 摘要，沒有逐字核對。未執行專案測試、worker、HTTP 或 DB。

## KH-018：資料庫原子性不等於流程排他：advisory lock 的鎖身份與釋放

**問題來源**（間接來源：question_memory 摘要，Codex 時期，不是原文）：2026-10-13 問既有的資料庫原子性與唯一約束，是否已經保護同一個 slot、還需不需要自己寫 mutex（[Q-20261013-youbike-atomicity-exclusion](../../question_memory/entries/Q-20261013-youbike-atomicity-exclusion.md)）；同日要求詳細解釋「鎖身份」由來源編號和 UTC 半小時序號推導的意義、來源與計算（[Q-20261013-youbike-slot-lock-identity](../../question_memory/entries/Q-20261013-youbike-slot-lock-identity.md)）；10/14 確認成功釋放鎖時 `pg_advisory_unlock` 的回傳值是否應為 `True`（[Q-20261014-youbike-unlock-result](../../question_memory/entries/Q-20261014-youbike-unlock-result.md)）。

**為何收錄**：三題接連問的是「約束已經在，為什麼還要鎖」「鎖到底鎖了什麼」「釋放有沒有成功怎麼看」，屬原理追問，不是實作錯誤，不推定他不會。KH-014 講的是測試裡誰等誰（Event、子程序與鎖的互動）；這篇補產品端為什麼需要鎖、鎖的 key 怎麼來。

**白話重點**：

- **原子性只管「一次寫入要嘛全成、要嘛全不成」，不管兩個程序做事的先後。** 產品的 raw 與站點寫入各自有交易，`raw_bytes.fetched_start_at` 唯一、`response` 的 (station_id, fetched_start_at) 唯一，所以同一個 slot 不會成功寫兩份。但兩個程序仍可能都先把 HTTP 下載完，第二個到 INSERT 才撞到唯一約束而失敗：資料沒壞，卻白打了一次 API、白跑了一次解析。要讓同一個 slot 一次只有一個程序在做「下載 → 寫 raw → 載入」，需要跨程序的排他。
- **不需要自己寫 mutex 演算法**，用 PostgreSQL 內建的 advisory lock，Python 只負責呼叫取得與釋放。一般的 `threading.Lock` 只在同一個程序內有效，跨不了獨立程序；`ON CONFLICT` 可以處理寫入衝突，但不會取消已經發出的 HTTP。
- **鎖身份＝「大家正在搶同一份工作」的編號**，不是每個程序自己的身份。`pg_try_advisory_lock(key1, key2)` 可以用兩個 32 位元整數當 key：第一個是約定好的來源編號（產品裡的 `Source.YOUBIKE.value`），第二個是該 UTC 半小時 slot 的序號 `int(秒 // 60 // 30)`。同來源同 slot 得到同一組 key；不同來源或不同 slot 就是不同的鎖。key 不能用每次都不同的東西（batch 的 UUID、PID、隨機值），否則兩個程序永遠搶不到同一把鎖。
- **`try` 版不等待**：搶不到就立刻回 `False`，所以產品讓後到的程序記一則 warning 就 return；沒有 `try` 的 `pg_advisory_lock` 才會等。session 層級的鎖會一直持有到釋放或連線結束，所以取得與釋放要用同一條連線、同一組 key。
- **釋放的回傳值**：`pg_advisory_unlock` 成功釋放回 `True`；這條連線沒有持有該 key（參數不同，或已經釋放過）回 `False`，伺服器還會報 warning。它是資料庫回傳的結果，不是自己設定的旗標。[PostgreSQL 16 advisory lock 函式](https://www.postgresql.org/docs/16/functions-admin.html#FUNCTIONS-ADVISORY-LOCKS)

**小例子**（售票情境，依官方規則推得的示意，未連 DB 執行）：

```text
-- 連線 A
SELECT pg_try_advisory_lock(1, 42);   -- true ：取得
-- 連線 B（同一組 key）
SELECT pg_try_advisory_lock(1, 42);   -- false：立刻回來，不等待
-- 連線 A
SELECT pg_advisory_unlock(1, 42);     -- true ：釋放成功
SELECT pg_advisory_unlock(1, 42);     -- false：已經沒有持有，並有 warning
```

slot 序號的算法（Python 3.9.6 實算）：`2026-09-25T06:00:00Z` 到 `06:29:59Z` 都是 994620，`06:30:00Z` 起是 994621；也就是每 1800 秒換一格，數字遠小於 32 位元整數的上限。

**在專案哪裡用**：[youbike.py](../src/extract/youbike.py)（10/14 15:27 存檔）的 `extract_youbike()`：`slot_key = (Source.YOUBIKE.value, half_hour_slot_id)`；在 `with psycopg.connect(..., autocommit=True) as conn:` 內先 `pg_try_advisory_lock`，搶不到就記 warning 後 return；重播路徑與寫入路徑做完後各自 `pg_advisory_unlock`，回傳 `False` 時記 warning。測試端怎麼讓兩個程序重疊，見 KH-014。

**容易搞混**：

- 「有唯一約束」≠「不會重複做工」：約束保護資料不重複，不保證不重複下載。
- 鎖身份不是 PID，也不是 batch_id，而是「這份工作」的編號。
- session 層級的鎖在連線結束時資料庫也會自動釋放（官方文件）；產品仍明確 `unlock` 並檢查回傳值，是為了在沒釋放成功時留下 warning。

**一句話記法**：約束保護「資料不重複」，advisory lock 保護「工作不重複做」；鎖的 key 是「來源＋slot」這份工作的編號。

**核對與限制**：規則依 PostgreSQL 16 官方文件與 10/14 存檔快照；slot 序號以 Python 實算；Codex 時期問答只有摘要，沒有逐字核對。本次未連 DB、未執行測試，不宣稱 Andrew 已獨立掌握。
